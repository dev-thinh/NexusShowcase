# Optional conference metadata

Approved in conversation: both research papers and projects/products may opt into conference metadata. Name is required when enabled; conference date, acceptance/publication date and rankings are optional and can be added later. Rankings are repeatable system/rank pairs entered as text, without claiming independent verification. The submitter remains separate from contributors; no automatic authorship or permission change.

Conference publication status is separate from visibility or publication on the club website. The author explicitly chooses ACCEPTED (Đã chấp nhận) or PUBLISHED (Đã công bố). Public cards and detail show the acceptance date for ACCEPTED and publication date for PUBLISHED; they never infer the status from the event date. Both dates remain stored across status switches. Event date stays a separate optional detail field. Historical conference values without a status default to ACCEPTED; absent metadata means no conference block.

Approach: one nullable structured JSON conference value travels through draft, revision, review, approval and publication. This avoids scattered fields and preserves multiple ranking systems. A conference catalog/external ranking lookup would introduce maintenance outside this request. Use date-only ISO strings, bounded text and at most eight ranking pairs. Switching between research and projects retains metadata. Published edits remain private until approved.

UI: use existing field styling and colors. A checkbox reveals conference fields for either type. Status selector controls the active date field; both dates remain editable by switching status. The two-line abstract is always preserved. A shared thin light-blue conference banner (background #eaf3fb, border #c7dced, navy text #153d67) spans the entire card above image and body; it contains name, event date, active milestone date and compact ranking chips. Wide cards use one row; narrow cards put the conference name on its own line (up to two text lines), then keep ranking and date groups together and right-aligned, wrapping whole groups only when necessary. Readable rank values take priority over long ranking-system labels. The standard badge/year/admin-controls header stays separate underneath. Long names truncate and detail navigation exposes full metadata for keyboard/touch. Card bodies have equal compact dimensions independently of the banner: no equal-height outer rows, no flexible expansion that makes ordinary cards taller to compensate for a banner. Titles use one truncated line, abstract keeps its two-line region, and footers follow content without auto-margin whitespace. Optional banners add only their own height. Banner dates align right, ordered after rankings as event date then acceptance/publication date. Reuse on homepage and both categories; full metadata appears in previews and detail. Citation output is unchanged.

Existing developer-account visibility edits are unrelated and must be preserved. No commit, push, or server account changes are part of this request.


Responsive audit: use a single 1280px threshold for desktop public navigation, account-label visibility and menu close-on-resize. Below it, keep logo/account/menu in one row with the existing accessible dropdown. Research photos have no stagger offsets and align from 768px upward; mobile remains stacked. Publication thumbnail images use contain so wide logos are not cropped. Tests cover 320–1440px, including 640/768/900/1024/1100/1279/1280 transitions and signed-in header overlap.
