# Asset registry operations

New uploads retain their canonical application URL, storage provider, provider file ID, optional owner, creation time and origin privacy state in `assets`. A duplicate URL is rejected rather than silently reassigned. Apply the additive registry migration and generate Prisma before rolling out upload writers. If registry insertion fails, the writer attempts to remove only the file it just created; failed rollback can leave an unknown provider object, which must be retained for manual reconciliation.

Run `npx tsx scripts/inventory-asset-registry.ts` for a read-only inventory and proposed legacy reconciliation. It checks avatars, gallery photos, live content, author drafts, historical revisions, editorial overrides, links and attachments. Failed reads, malformed structured content and ambiguous absolute upload URLs make provenance incomplete. The script does not invent cloud file IDs, owners, upload dates or privacy state and does not change legacy records.

Run `npx tsx scripts/cleanup-orphan-assets.ts` for a dry run. `--grace-days=N` must be at least seven. Only registry-owned ImageKit objects with a known provider ID and complete reference provenance can be proposed. Referenced, recent, already quarantined and deleted objects are retained.

`--apply` requires the reference-guard migration and explicitly deletes eligible registered ImageKit objects. It claims the registry row after a fresh serializable reference check. Database triggers acquire shared asset locks for new references across all seven source tables and reject references to claimed/deleted objects. After the claim commits, cleanup inventories references again before the provider operation. It also scans concrete managed URLs in checked-in `src` and `prisma` files. Avoid concurrent deployments that change static asset references during a cleanup run. Dynamically assembled source paths cannot be proven by this scan; reconcile those before applying cleanup.

Malformed references, unknown legacy ImageKit URLs and missing guards block deletion. Inventory and guards decode printable ASCII percent escapes, Unicode escapes and decimal/hex HTML numeric entities repeatedly for up to eight passes. Guards lock only matching canonical asset paths; unrelated encoded text remains writable. Unsupported or deeper encodings make inventory incomplete. Serializable conflicts stop the command. A failed or interrupted provider operation leaves the row quarantined; inspect both provider state and references manually before releasing a quarantine or recording completed deletion. The command intentionally does not automatically retry interrupted claims. Database administrators can bypass triggers; do not disable guards or edit registry identities during cleanup.

No inventory command lists all objects in the connected ImageKit account. Objects absent from the registry remain unknown and must be retained. On 2026-10-25 the three additive hardening migrations were applied transactionally to the existing runtime schema after collision and schema-diff checks. Existing accounts and content were unchanged; unmanaged migration history was not rebased. Legacy reconciliation writes registry rows only after delivery/privacy verification. Orphan deletion has not been applied.

## Legacy ImageKit privacy reconciliation

Run `npx tsx scripts/reconcile-imagekit-assets.ts` for a dry-run proposal. It reads metadata only within the configured project upload folder and selects exact canonical paths that a complete reference inventory identifies as publicly used (visible gallery, active avatar or published public content). Restricted-only, unknown and unreferenced objects are left untouched. Review the proposal before separately running with `--apply`.

Apply rechecks provenance and existing registry identity, reads original bytes through a server-signed URL, and reuploads those same bytes at the same path with private origin enabled. Metadata overwrite flags preserve existing tags and custom metadata. It confirms provider privacy, compares SHA256 of signed reads before and after, then requires both unsigned original URL forms to deny access with 401/403 before recording `private=true`. Existing registry owners remain unchanged. Any mismatch stops the run; a partially completed object can remain private without its registry privacy being confirmed and requires inspection before retrying. Coordinate uploads and content changes during this operation to avoid overwriting concurrent edits. It never deletes objects. By default, it does not purge caches.

Explicitly add `--apply --purge-cache` only after reviewing the exact-object reconciliation proposal. If unsigned access checks still succeed, this option submits cache purges for exactly the current object's bare original URL and its `?tr=orig-true` URL. It never submits wildcard or account-wide purges. Purge status polling shares a bounded 30-second deadline with waits of at most one second; failures and timeouts stop reconciliation. Both unsigned URLs must subsequently return 401/403 before registry privacy is confirmed. This option requires separate explicit operator intent and cannot be used without `--apply`.

Origin privacy cannot retroactively recall bytes already downloaded or retained in public browser/CDN caches. A CDN response that still serves unsigned bytes blocks registry privacy confirmation; investigate provider delivery settings and cache behavior separately. Previously shared public content must be treated as previously disclosed.

Provider field semantics: [ImageKit upload API](https://imagekit.io/docs/api-reference/upload-file/upload-file), [ImageKit list/search API](https://imagekit.io/docs/api-reference/digital-asset-management-dam/list-and-search-assets), [CDN caching and purging](https://imagekit.io/docs/cdn-caching-and-purging), [provider purge-status API](https://www.postman.com/imagekitio/imagekit-apis/request/aie7j8r/get-purge-status).
